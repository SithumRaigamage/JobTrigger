## E2 — Demo mode (store-review blocker)

**Problem (verified):** nothing in the app, website or backend offers a way
in without your own credentials. App Review signs in with an account you
give them, but the app then calls Jenkins **directly from the phone**, so the
reviewer needs a Jenkins server their device can reach. Without one,
the app looks empty or broken, which is a common rejection reason.

**Approach:** demo data runs on the device, from in-memory repositories. No
public Jenkins server, no real credentials anywhere, no backend writes. This
fits the layers in `docs/architecture.md`: demo mode swaps repository
implementations through Riverpod overrides. Widgets don't change, and no new
dependency is needed.

**Decided (recommended, 2026-11-14): read-only, plus one scripted build.**
Browsing is read-only. The one exception is "Build now" on a single demo
job, `demo-app/main`: it plays a scripted run (queued → stages → a log that
streams line by line → success, about 20 seconds), all in memory. That is
the app's core moment, which a reviewer or new user should see. Every other
write action (cancel, approve, replay, parameters, credential edits) shows
"Not available in demo". Why not fully read-only: an app whose main button
does nothing in the demo looks broken to a reviewer. Why not simulate
everything: more fake code to maintain, and it blurs what's real.

*App*
- [ ] PE-10 `lib/data/demo/`: `DemoJenkinsRepository`,
      `DemoGitHubRepository`, `DemoSonarQubeRepository`, implementing the
      existing domain interfaces with fixed sample data (a folder tree, a
      pipeline with stages, a failed build with a readable log, a running
      build, test results, a GitHub repo with runs, a SonarQube project with a
      failing gate). Build them from the shapes the existing test fakes use
      (`test/support/fake_jenkins_repository.dart`,
      `fake_github_repository.dart`), not by copying test code into `lib/`.
- [ ] PE-11 `DemoModeNotifier` (stored in `shared_preferences`, not secure
      storage, since it holds no secret). When it's on, the app's root
      `ProviderScope` overrides the repository providers with the demo ones.
      The real data layer is untouched.
- [ ] PE-12 Entry point: a "Try the demo" button on the sign-in screen.
      Demo mode skips sign-in and the backend entirely. A persistent "Demo"
      banner, with "Exit demo", returns to sign-in and clears demo state.
- [ ] PE-13 Write actions in demo: "Build now" on `demo-app/main` plays the
      scripted run through the existing live-status and log screens (the demo
      repository returns the stages and log in timed steps). Every other write
      action shows "Not available in demo". The decision lives in a notifier,
      not in widgets (`CLAUDE.md` §5). The scripted run resets when demo
      mode exits.
- [ ] PE-14 Make sure demo mode never touches real data: it must not read
      secure storage, refresh the widget snapshot from real servers, run
      background build checks (`workmanager`) or send analytics.
      Tests for each.
- [ ] PE-15 Tests: notifier unit tests, a widget test per main screen in

*Website*

## E3 — Crash and error reporting (blind at launch)

**Problem (verified):** no crash or error reporting in any of the three
projects. Not in `pubspec.yaml`, `JobTrigger-Web/package.json` or
`JobTrigger-Backend/package.json`, and no `FlutterError.onError` or
`PlatformDispatcher.onError` handler in `lib/`. Skipped on purpose in P6-08
"until before public release" (`tasks/backlog.md`).

**Decided 2026-11-14: GlitchTip, self-hosted in the DevOps lab**
(`/Users/sithumraigamage/Other/02-DevOps-Lab/custom-devops-stack`). The lab's
own `docs/TOOLS-ROADMAP.md` already lists GlitchTip as "planned next for
JobTrigger crash reports", reusing `postgres/`. GlitchTip accepts the
Sentry SDKs, so the three projects use `sentry_flutter`, `@sentry/nextjs`
and `@sentry/node`, pointed at GlitchTip. Those three packages go into the
`CLAUDE.md` §3 table and `docs/web-architecture.md` in the same PR that adds
them (approved with this phase).

**On in development and production (decided):** every event carries
`environment: development | production` and `release: <version>+<build>`,
so the two never mix. One GlitchTip project per app (`jobtrigger-app`,
`jobtrigger-web`, `jobtrigger-backend`). Errors are sent at 100%.
Performance tracing is off, to keep the lab light (8 GB Mac).

**Production host (recommendation):** the lab runs on a Mac that sleeps and
isn't public, so release builds can't count on reaching it. Use the lab
instance for development now, and deploy the same compose file next to the
production backend when it goes live (P15-22). Until then, production
events wait in the offline store below. The DSN comes from config, so
switching hosts is configuration only.

**Offline fallback (recommendation for "if offline, write it to a file"):**
- *App:* `sentry_flutter` already writes unsent events to disk on the
  phone and sends them on the next launch when online. Use that, capped at
  30 events (`maxCacheItems`), not a file of our own. The cache sits in the
  app's sandbox, and events are scrubbed *before* they are cached, so no
  token ever reaches disk. **(check: confirm the SDK version's offline
  caching and `maxCacheItems` at implementation)**
- *Website (browser):* the Sentry browser SDK's offline transport keeps
  unsent events in IndexedDB and retries. **(check the transport name and
  options for the installed `@sentry/nextjs` version)**
- *Backend and website server:* a small wrapper transport. When GlitchTip
  can't be reached, it appends the scrubbed event as one JSON line to
  `crash-outbox/YYYY-MM-DD.jsonl` (gitignored, mode 600), capped at 10 MB
  and 7 days. It retries the outbox on startup and every 5 minutes, and
  deletes lines once they are accepted. The backend's normal error log line
  still goes to stdout, which the lab's Promtail already ships to Loki.
- Never write an unscrubbed event anywhere, online or offline.

## E4 — Credential encryption: production setup and hardening

**State (verified):** AES-256-GCM encryption at rest is done (AUD-03), with
key rotation, a backfill script and a startup key-id audit (AUD-63). The
website never holds a secret in the browser (`domain/mask.ts`).

**One real gap:** the app calls Jenkins, GitHub and SonarQube directly, so
it needs the secret, and the backend decrypts on `toJSON`
(`models/plugins/encryptedFields.js`). That means **every credential list
response carries every decrypted secret**. That is by design for the
direct-to-Jenkins architecture. But "no plaintext in API responses" can't be
fully met without a proxy, which `docs/architecture.md` rules out. The
hardening below narrows it instead.

*Backend*
- [ ] PE-30 **Owner action:** production key in the host's secret manager
      (not in a file), a second key id ready for rotation, and the
      rotation steps in `docs/deployment.md`.
- [ ] PE-31 **Owner action:** back up, then run
      `node scripts/encrypt-credentials.js --dry-run` and then without
      `--dry-run` on the production database. Confirm the startup audit
      reports no unreadable key ids.
- [ ] PE-32 **Decision:** list responses return metadata and a masked
      secret only. Add `GET /api/<tool>/credentials/:id/secret` (owner-only,
      rate-limited, `Cache-Control: no-store`) for the decrypted value.
      Existing list tests change on purpose, and the commit says so
      (`CLAUDE.md` §11).
- [ ] PE-33 A test that no log line from any credential route contains a
      secret (extend `credential_resilience.test.js`).

*App* (only if PE-32 is approved)
- [ ] PE-34 Credential repositories fetch the secret through the new
      endpoint when a server becomes active, keep it in
      `flutter_secure_storage` only, and drop it on logout. Add a
      tool-specific case for each repository. Jenkins changes only in its
      credential data source; its screens and behaviour stay as they are.

*Website* (only if PE-32 is approved)
- [ ] PE-35 The portal uses the masked value from the list response and
      never calls the secret endpoint.

**Verify:** after PE-31, a document read straight from MongoDB shows
`enc:v1:…` for every secret field.
